# 产品功能与界面确认

## 何时读取

在确认或修改产品目标、主要功能、用户流程、页面数量、页面职责或非 UI 操作面时读取。新增功能先进入本阶段，再判断是否需要 UI、架构和实现工作。

## 必须读取

- `PROJECT_BRIEF.md` 及其中索引的原始素材；
- `PROJECT_STATE.md`；
- 已存在的 `PRODUCT.md`；
- 与当前变更有关的真实实现和用户反馈。

## 本阶段负责决定

- 产品解决什么问题，面向谁以及当前范围；
- 用户需要完成的主要过程和功能；
- 需要哪些页面、屏幕、命令、服务或其他操作面；
- 每个操作面负责什么，不负责什么；
- 哪些内容明确不做，哪些仍是候选。

本阶段不决定静态布局、美术风格、后端拓扑、数据库或具体接口。

## 工作方式

从初始化简报中的核心功能候选开始，帮助用户把想法变成可理解的产品行为。先梳理用户要完成的任务和完整过程，再推导页面；不要先画一组页面后反向发明功能。

只追问会改变功能边界、用户过程或页面职责的未知。可以暂时保留次要功能和边界状态，不要求一次定义完整产品。

把确认结果写入 `PRODUCT.md`。小型产品使用一个文件；内容过大时可以拆分详细功能文档，但 `PRODUCT.md` 必须保留权威索引。

推荐结构：

```markdown
# Product

## 目的与范围
- 问题、预期结果和当前范围：...
- 明确非目标：...

## 用户与情境
- 用户、使用情境和约束：...

## 核心用户流程
1. ...

## 功能
| 功能 | 用户价值 | 规则 | 状态 |
|---|---|---|---|

## 操作面清单
| 页面或操作面 | 目的 | 功能 | 重要状态 | 依赖 |
|---|---|---|---|---|

## 跨操作面规则
- 多处共享的术语、权限和行为：...

## 开放决定
- ...
```

页面清单描述目的、功能和重要状态，不描述像素、配色或组件造型。没有 UI 的能力同样需要出现在功能和操作面中。

发现用户的新想法时，先标记为 `candidate`；只有用户确认或明确授权 Agent 决定后，才把它变成正式功能。

## 用户确认点

- 产品目标和当前范围；
- 核心功能、主要用户过程和明确非目标；
- 页面或其他操作面的数量、职责与重要状态；
- 会显著扩大成本或改变产品定位的新功能。

## 持久产物与退出门槛

产出或更新 `PRODUCT.md`，并在 `PROJECT_STATE.md` 中登记其批准状态。

当主要功能和操作面已经足以开始视觉探索、技术选型与架构设计，用户确认当前范围，且开放问题不会阻塞这些工作时停止。不要求所有未来功能和边界情况都已决定。

## 影响检查

- 功能、流程或操作面变化：复查 UI、技术基础、架构、接口、实现和测试；
- 仅文字说明更清楚且行为未变：不自动重开其他阶段；
- UI 探索发现缺失状态或页面：返回本阶段确认后更新 `PRODUCT.md`；
- 架构限制改变用户行为：返回本阶段让用户确认产品取舍。
