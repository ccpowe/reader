# 新项目初始化

## 何时读取

在用户从零散想法、素材、空目录或尚未形成产品的脚手架开始时读取。既有项目中的普通功能、设计或架构变更不进入本阶段。

## 必须读取

- 用户当前对话中提供的全部想法、文件、图片和链接；
- 当前工作目录中适用的上层 `AGENTS.md`；
- [project-contracts.md](project-contracts.md)。

## 本阶段负责决定

- 用户当前想法和素材应如何被忠实保存与整理；
- 足以进入产品阶段的目标平台、产品形态、核心功能候选和技术偏好；
- 项目文档、素材、版本控制和 Agent 导航的最小工作区结构。

本阶段不选择技术栈，不安装产品依赖，不创建前后端脚手架，也不创建 `PRODUCT.md`、`DESIGN.md` 或架构文档。

## 工作方式

### 1. 接住并保存全部输入

先邀请用户自由表达，不从问卷、技术选项或文档模板开始。允许内容零散、矛盾和暂时不现实；用户仍在补充时先倾听、复述和连接信息。

把输入写入 `PROJECT_BRIEF.md`。保留用户原意和素材来源，不要只留下 Agent 的摘要：

```markdown
# Project Brief

## 原始想法与素材
- [用户原始表述、文件路径或 URL，以及用户看重的部分]

## 梳理后的理解
- 要解决的问题与预期结果：...
- 目标用户或使用情境：...
- 目标平台与产品形态：...
- 核心功能候选：...

## 偏好与约束
- 技术偏好：...
- 现实约束：...

## 视觉探索输入
- 参考、氛围、喜欢与排斥内容、候选方向：...

## 决定状态
- 已确认：...
- 已授权 Agent 决定：...
- 候选：...
- 开放或冲突：...
```

将本地素材保存在 `docs/context/assets/` 或等价稳定位置，不覆盖原件；无法复制时记录现有路径。外部素材记录 URL、来源和用户具体关注点。不要把候选功能或视觉偏好升级为已批准结论。

### 2. 只追问影响产品梳理的未知

判断目标平台、产品形态、核心使用过程、主要功能候选和已知硬约束是否足以进入产品阶段。它们是收敛目标，不是固定问题清单。

先展示整理结果，再询问会导致 Agent 无法正确理解产品起点的最小未知集合。完整页面清单、技术选型、边界状态、数据模型和商业细节留给负责阶段。

### 3. 建立项目工作环境

- 创建保存简报、素材和后续权威文档所需的最小目录；
- 初始化 Git，并创建保护秘密、本地产物和临时文件的基础 `.gitignore`；
- 创建 `PROJECT_STATE.md`，登记简报已就绪，产品、UI、技术基础和架构仍待处理；
- 创建简短的根 `AGENTS.md`，说明文档入口、素材位置、安全边界和当前不得提前实现或选择完整技术栈；
- 不写框架、依赖、命令或尚不存在的目录规范。

这个根 `AGENTS.md` 是发现阶段的工作说明。产品确认并建立技术环境后，由架构阶段根据真实项目和官方指导扩充，并按需创建局部文件。

## 用户确认点

- Agent 对用户全部输入的整理是否准确；
- 原始素材和参考是否被正确索引；
- 仍然开放或互相冲突的内容是否被正确标记。

## 持久产物与退出门槛

产出 `PROJECT_BRIEF.md`、必要素材、基础目录、Git、最小根 `AGENTS.md` 和 `PROJECT_STATE.md`。

当用户确认整理结果，后续 Agent 能找到原始想法与素材，并且产品阶段可以继续梳理功能和操作面时停止。没有安装产品依赖，也没有提前形成技术、产品或设计契约。

## 影响检查

- 把核心功能候选、平台和产品形态交给产品阶段；
- 把视觉素材和偏好交给 UI 阶段，但保持 `candidate`；
- 把技术偏好和现实约束交给技术基础与架构阶段；
- `PROJECT_BRIEF.md` 中的平台或硬约束以后变化时，复查产品、UI、技术基础、架构和实现。
