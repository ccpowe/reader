# 质量审查与交付

## 何时读取

在审查、加固、优化、处理高风险改动、准备发布或确认阶段产物是否达到交付质量时读取。实现阶段也可以按当前风险选择本文件中的相关检查。

## 必须读取

- 当前改动涉及的产品、设计、架构和接口权威；
- 适用的 `AGENTS.md` 与验证命令；
- 代码差异、测试和真实运行结果；
- `PROJECT_STATE.md` 中标记为 `needs-review` 的项目。

## 本阶段负责决定

- 哪些风险需要额外证据才能交付；
- 实现是否满足已有契约和质量底线；
- 问题应在当前代码修复，还是返回产品、UI 或架构阶段；
- 哪些文档必须根据最终实现校准。

本阶段不重新发明产品、视觉或架构目标。

## 工作方式

根据改动范围和失败代价选择检查，不运行一份与任务无关的巨型清单。至少从以下方面判断适用项：

- 产品功能、权限、错误和边界行为；
- UI 视觉一致性、响应式、重要状态、可访问性和交互反馈；
- 前后端协议、数据完整性、并发、迁移和恢复；
- 安全、隐私、秘密、依赖和信任边界；
- 性能、资源、兼容性和可观测性；
- 代码结构、重复、可测试性和 Agent 可导航性。

前端审查使用真实页面、真实路由和代表性内容；比较获批 Penpot 与实现，但以真实应用验证动画、交互和运行状态。后端与接口审查使用测试、日志和可重复请求，不只阅读代码。

先记录可复现证据、影响和严重度，再修复获得授权且范围明确的问题。修复后运行针对性回归验证。发现权威契约本身有问题时返回对应阶段，不以“质量优化”名义改变目标。

后续从 Impeccable 或其他方法吸收审查规则时，只把经过真实项目验证、能改善特定风险的规则加入这里或专用 reference；不要恢复成独立流程控制 Skill。

## 用户确认点

- 质量、时间、性能、成本或兼容性之间的实质取舍；
- 会改变获批体验或公共行为的修复；
- 已知风险是否可以接受并交付。

## 持久产物与退出门槛

修复确认的问题，保留必要测试和简洁证据；同步最终代码事实到产品、设计、架构、接口、项目地图和 `AGENTS.md`。解决或明确接受 `PROJECT_STATE.md` 中受影响的 `needs-review` 项。

当适用验证通过、没有未说明的高风险问题、文档与真实实现一致、用户确认必要取舍时，当前交付可以结束。

## 影响检查

- 功能不符合目标：返回产品阶段；
- 静态视觉或布局缺陷：返回 UI 阶段；
- 系统或协议缺陷：返回架构阶段；
- 局部实现缺陷：返回实现阶段；
- 修复改变任何权威后，重新运行该权威对应的影响检查。
