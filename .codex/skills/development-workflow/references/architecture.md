## 何时读取

在 `PRODUCT.md` 已足以描述主要功能和操作面，需要选择技术栈、建立代码环境，或确定系统边界、后端、数据、部署、安全和前后端协议时读取。可以与 UI 设计并行，不必等待全部静态页面完成。

## 必须读取

- `PROJECT_BRIEF.md` 中的平台、技术偏好和现实约束；
- `PRODUCT.md` 中的功能、流程、操作面和重要状态；
- `PROJECT_STATE.md`；
- 已存在的 `ARCHITECTURE.md`、接口定义、`AGENTS.md` 和真实实现；
- 已获批 UI 中会影响数据、延迟、权限或实时行为的状态。

## 本阶段负责决定

- 实现产品所需的完整技术基础、项目结构和官方开发规范；
- 系统组件、责任边界与部署单元；
- 客户端、前端、后端、数据存储、鉴权和外部集成；
- 数据所有权、关键流程、失败处理和安全边界；
- 前后端接口、事件或消息协议及其演进方式。

本阶段不决定产品功能是否值得做，也不决定页面的静态视觉风格。

## 工作方式

### 1. 推导技术要求与最小系统形态

从主要用户流程逐一提取平台能力、实时或离线要求、设备访问、数据、安全、部署和运维约束。先判断单体或分离、本地或云端、客户端与服务端等足以约束技术选择的基本边界，不为未确认的未来需求建立复杂抽象。

### 2. 委派当前技术调研

按语言、框架、平台或基础设施拆分边界清晰的研究 Subagent。Subagent 不修改项目文件，也不替用户批准，只返回：

```markdown
- 当前受支持版本与生命周期
- 官方来源
- 官方 AGENTS/AI 指南及适用范围
- 适用于应用开发者的规则
- 不得复制的框架贡献者专用规则
- 官方脚手架和验证命令
- 与产品要求的适配证据
- 兼容性、许可、托管和迁移风险
- 剩余未知项
```

优先使用官方文档、仓库、发布说明和支持政策。官方资料不足时才参考同技术和产品形态的活跃知名项目，并标记为参考惯例。Subagent 不可用时，由主 Agent 按同一结构调研并记录限制；不要只凭模型记忆选择当前技术。

### 3. 推荐并确认技术栈

主 Agent 综合产品要求、最小系统形态和研究结果。用户有偏好时验证适配性；没有偏好时给出一个首选建议，只在存在实质取舍时列出少量替代方案。

获得必要确认后，把版本、理由、来源、高切换成本决定和延后事项写入 `ARCHITECTURE.md`。只有需要独立保留历史的重大决定才创建 ADR。

### 4. 建立代码技术环境

使用已核对的官方方式：

- 安装语言、运行时、包管理器、框架和基础依赖并生成锁文件；
- 根据已经确认的系统边界创建客户端、前端、后端和共享目录；
- 配置适用的格式化、静态检查、类型检查、测试和构建入口；
- 建立环境变量示例与秘密边界；
- 按实际技术栈补充 `.gitignore` 中的依赖、构建和本地产物规则；
- 扩充根 `AGENTS.md`，写入真实技术、目录、文档导航和已验证命令；
- 只为不同语言、框架、命令或安全边界创建局部 `AGENTS.md`；
- 实际运行所有适用命令，确认脚手架能够继续开发。

先确认外层 Git 已由初始化阶段建立；缺失时补充，不把版本控制作为本阶段的中心。不要整份复制框架仓库的 `AGENTS.md`，先区分应用作者规则与框架贡献者规则。

只保留中性入口，不提前实现正式页面、动画、业务功能或完整数据模型。

### 5. 完成架构与接口契约

推荐 `ARCHITECTURE.md` 至少说明：

```markdown
# Architecture

## 背景与约束
## 技术基础与来源
## 系统边界
## 组件与职责
## 数据归属与模型
## 核心运行流程
## 安全与信任边界
## 部署与运维
## 接口契约索引
## 重要决定
## 风险与开放问题
```

优先使用 OpenAPI、GraphQL schema、protobuf 或其他适合项目的机器可读格式作为接口权威。覆盖鉴权、输入输出、错误、分页或流式行为、版本和兼容规则；说明文档只补充 schema 无法表达的语义。

UI 和架构并行时，主动交换页面状态、数据与技术限制。不要让任一方凭假设静默继续。

## 用户确认点

- 技术栈和会造成明显平台锁定的选择；
- 会改变成本、隐私、运维负担或产品能力的架构决定；
- 第三方、付费服务、数据驻留和账号依赖；
- 技术限制要求改变用户行为的取舍。

## 持久产物与退出门槛

产出可运行的代码技术环境、根及必要局部 `AGENTS.md`、`ARCHITECTURE.md`、机器可读接口定义和必要 ADR，并更新 `PROJECT_STATE.md`。

当技术栈具有当前适配证据、环境命令已验证、核心功能都有责任归属、关键数据和失败路径可解释、前后端可以依据接口实现、重大风险已有决定或验证计划时停止。

## 影响检查

- 技术栈或目录变化：复查环境、所有 `AGENTS.md`、架构、实现、测试和 CI；
- 架构或接口改变用户可见行为：返回产品阶段；
- 新限制影响页面状态：通知 UI 阶段；
- 协议变化：标记前端、后端、契约与集成测试为 `needs-review`；
- 真实实现证明设计不可行：回到本阶段更新权威，不在代码中保留隐性架构。
