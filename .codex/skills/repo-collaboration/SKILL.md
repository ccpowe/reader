# 仓库文档体系

文档用于对齐项目能力、开发约定和架构边界，使实现与约定可以相互核对。用户已明确的文档范围与实际仓库约定优先；按现有内容和真实需要建立资料，不为凑齐结构创建空文件。

## 默认结构与定位

| 文档或资源 | 回答什么 | 维护内容 | 更新时机 |
| --- | --- | --- | --- |
| `README.md` | 项目是什么，能做什么，怎样开始使用？ | 产品定位、当前能力、使用限制、最短使用路径、资料入口 | 用户可感知的能力、使用方式或支持范围变化 |
| 根 `AGENTS.md` | 人和 AI 在整个仓库应怎样工作？ | 仓库级目录导航、共享环境与命令、开发约定、协作边界、验证与审查要求、文档维护规则 | 共享工作方式、命令、目录入口或开发约束变化 |
| 子系统 `AGENTS.md` | 在这个子系统中应怎样实现和验证？ | 本地目录与关键入口、环境和命令、具体开发约定及验证；继承根约定 | 本子系统的工作方式、命令、导航或实现约束变化 |
| `ARCHITECTURE.md` | 系统怎样组成，职责与数据属于谁，哪些边界要保持？ | 系统组成、模块职责、数据归属、依赖约束、关键运行流程、故障边界 | 职责、数据归属、依赖关系或关键运行机制变化 |
| `architecture/workspace.dsl` | 系统、运行单元和重要组件怎样关联？ | C1 System Context、C2 Container、C3 Component 及关系；C4 查看代码 | 相关系统、运行单元、重要组件或关系变化 |
| 系统边界接口定义；必要时 `contracts/` | 边界两侧怎样交换数据并处理结果？ | 实际采用的 OpenAPI、Protobuf、JSON Schema、AsyncAPI 等机器可读定义及生成链；遵循既有编写源 | 协议路径、字段、认证、错误、兼容性承诺或生成机制变化 |
| `docs/adr/` | 为什么作出这项重要架构决定？ | 有依据的背景、决定、实际比较过的选项、取舍及后果，明确决定状态 | 作出重要决定，或已接受决定发生实质变化 |

根 AGENTS 维护共享工作规则，前后端等子系统 AGENTS 只补充当地细节。按真实目录和复杂度设置子文件，不机械增加层级；共享规则引用根文件，不另行复制。

README 面向使用者，开发命令归 AGENTS，职责与数据所有权归 ARCHITECTURE。架构说明解释职责、约束和流程，DSL 表达结构与关系，ADR 解释决定的来由。允许简短概述与导航，同一详细事实只在负责它的位置维护，其他资料链接引用，不建立逐文件职责清单。

上表是默认信息分工，并非封闭清单。新增资料按实际信息需要和仓库约定确定：明确回答什么问题、面向谁、已有资料是否负责这些信息，以及什么变化触发更新。优先复用已有归属并避免重复；不因新增类别本身就要求重新询问用户，仍遵守任务范围和项目约定。默认结构不构成删除或替换已有资料的授权。

不为每个任务自动生成永久计划、总结或验收记录。跨会话接续、多人协作或明确交付确有需要时，可以保留必要记录，遵循项目规定的位置和维护方式，避免留下无人维护的重复资料。

## 事实与维护规则

文档依据源码、接口声明、运行配置和有效验证证据，明确区分“当前实现”“已确认但尚未实现的目标”“未知”。文档与代码不一致时，需要判断文档过期、实现偏离还是目标变化；不能把实现缺陷改写成预期行为，也不能把旧方案未经核对地当作当前约束。

架构模型默认维护 C1–C3 及关系，C4 直接查看源码。只有确需表达运行时交互或部署问题时才增加 Dynamic View、Deployment View。DSL 是维护源，预览导出遵循仓库的生成和忽略规则，不手改导出物。

接口遵循实际编写方式：代码优先就修改代码中的声明，协议优先就修改协议源，再由对应工具生成快照、客户端或类型并检查同步。不能为同一协议手写第二份定义，也不能只更新生成文件。`contracts/` 按真实边界需要设置，没有服务间通信或事件协议时不创建对应空目录或规范。生成物是否提交遵循仓库约定。

ADR 草稿可以持续修订；已接受决定发生实质变化时新增记录并关联被替代项，原记录保留决策历史。只记录有依据的决定及理由，不从现有代码反推虚构的历史讨论或用户批准；无法核实的缘由明确未知。

## 不同项目阶段

- **新项目**：建立当前目标所需的最小资料。尚未实现的能力明确标为目标，未知命令、接口和运行机制不写成已验证事实。模型、协议和子目录约定对应真实需要，不为了凑齐文档而拆服务或增加基础设施。
- **旧仓库重建**：从源码、配置、接口、测试和生成脚本重建现状，旧文档仅作线索，区分有效、重复、过期和未知内容。先迁移独有且有效的信息，按已授权范围退役旧资料并修正引用；文档重建本身不包含顺便重构代码，也不能补造历史决定。
- **日常变更**：相关资料随实现同步，只更新受影响的事实与约束。某类文档无需更新时说明依据，不要求每次修改全部文档或重建整个体系。

## 一致性标准

- 文档所述能力、使用限制、命令和目录有可核对的依据；链接有效之外，还需确认所指内容能够支持相关说明。
- 职责、数据归属、依赖与关键流程对应实现和已确认约束；模型与文字描述之间没有未说明的冲突。
- 接口源、生成快照或类型同步，协议描述和调用行为一致；生成检查不能代替兼容性判断。
- 文档没有将未实现目标标为当前能力，没有用修改描述掩盖缺陷，也没有丢失仍然有效的独有信息。

验证强度与变化相称，遵循仓库约定。只有文档调整时核对事实、路径、命令来源、链接及差异，不默认启动完整应用构建。
