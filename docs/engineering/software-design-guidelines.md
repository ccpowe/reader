# 降低软件复杂度的开发规范

参考《[软件设计的哲学》中文版](https://cactus-proj.github.io/A-Philosophy-of-Software-Design-zh/)，以下条款供系统设计、代码编写与审查时作为补充规范。适用于后端与通用设计；App（React）代码在此基础上按 [React 开发规范](react-guidelines.md) 编写与自查。

## 总体判断

以**降低系统整体复杂度**为首要目标：让常见任务更容易理解、实现和修改。复杂度不是代码行数或模块数量，而是完成任务所需的知识、判断、跨处修改和出错风险。重点关注三类信号：一处决策变更是否牵动多处（变更放大）；开发者是否必须记住太多前置知识（认知负荷）；是否难以发现哪些部分需要修改或存在什么隐含约束（未知的未知）。依赖和晦涩是复杂性的主要来源。

这些原则是用于比较方案、暴露风险的设计启发，不是必须机械套用的规则。结合系统的真实需求、约束与维护场景验证每项取舍；若某原则在此处不能降低复杂度，就不要为了遵从它而增加复杂度。

## 核心设计与实现原则

- **工作代码不等于好设计。** 交付功能时，也要考虑后续理解、扩展与修复的成本。采用小步、持续的设计改进；让每次迭代在增加能力的同时改善或稳住抽象，而非只堆功能与补丁。
- **用清晰边界管理依赖。** 将系统拆分为职责连贯的模块；模块接口说明调用者必须知道的行为契约，实现细节尽量留在模块内部。优先选择“接口简单、内部实现可复杂”的深模块；避免接口暴露过多细节、浅层包装和无实质作用的透传方法。私有字段本身不等于信息隐藏，若访问器把内部表示完整暴露出去，依然形成依赖。
- **隐藏会变化的设计决策。** 检查某项知识（如数据格式、算法、策略或不变量）是否散落在多个模块，或因按运行时先后步骤切分而重复表达。尽量让相关知识由一个职责清晰的模块拥有，使实现改变时影响面可控；同时确保接口完整表达调用者正确使用模块所必需的信息。
- **抽象适度通用。** 模块能力满足当前需要，接口不必绑定某个单一用例；适度通用通常可减少特例和浅层方法。但不要为未经证实的未来需求构造庞大框架。把通用机制与特定场景策略分清，避免特定层的概念泄漏到通用模块。
- **让相邻层提供不同抽象。** 每层应完成有意义的转换或隐藏机制。若相邻层接口和职责几乎相同、方法只传递参数，重新检查职责归属：可移除中间层、重新分配行为，或在确实紧密耦合时合并。
- **按整体成本决定合并或拆分。** 共享关键知识、总是共同使用、概念紧密相关或难以分别理解的部分，可能适合放在一起；可独立变化、独立复用且边界清楚的部分，适合分开。拆分也会增加接口、组件管理、跳转和重复；不要把“更小的类/函数更多”当成设计质量。
- **把合适的复杂性留在最能解决它的模块内。** 若复杂性与模块职责紧密相关，且集中处理能简化常用接口和多个调用方，就由该模块承担，提供合理默认值，避免把策略、参数和重复处理推给每个使用者。若调用者确实掌握模块无法获知且有价值的领域信息，则保留必要配置或选择；不要为了“向下移”而混入无关职责。
- **减少可避免的错误状态。** 重新审视异常和特殊情况的定义；若操作语义允许，可使重复执行、缺省状态或边界输入成为自然的正常行为，从而减少调用方必须处理的分支。对真实失败仍须按契约明确报告、恢复或传播；不要以吞掉错误、掩盖数据损坏来换取表面简单。异常属于接口契约，应控制数量并在合适层处理。
- **重要设计不要止于第一个想法。** 对影响范围较大的系统分解、接口或实现，至少比较两个有实质差异的方案；权衡常见用法的简单性、抽象深度、适度通用性、实现复杂度、性能及演进成本，再选取或综合方案。无需为小改动徒增形式化流程。
- **把注释当作抽象与设计的一部分。** 先写或先审视模块/方法的接口说明，再实现核心逻辑。说明目的、行为、参数与结果含义、重要约束、副作用及调用者必须了解的错误条件；实现注释补充代码中不显然的理由、策略、不变量和跨模块依赖。不要逐行复述代码，也不要把实现细节塞进面向调用者的接口说明。注释应靠近所描述的代码，并随行为变更更新；难以简短完整地说明一个接口或变量，是重新检查其抽象与职责的信号。
- **精确命名并保持有意义的一致性。** 名称应让读者准确判断实体是什么、代表什么状态或范围，避免含糊的通用词、容易混淆的概念和无法表明含义的布尔名。遵循项目既有术语、风格和约定；相似概念用相似表达，不同概念不要为了表面统一而混为一谈。代码以读者易理解为先；用清晰结构、格式、注释补足无法避免的隐含控制流。
- **修改现有代码时保持战略性。** 先理解局部约定及关联模块，再选择能安全满足需求且不制造特殊分支、重复知识或新泄漏的方案。若合理且可验证，趁修改之机小幅重构并更新相关注释；时间、兼容性或风险有限时，记录折衷和后续清理点，不以无边界重写代替判断。
- **评估新范式与性能优化时仍回到复杂度。** 面向对象、继承、设计模式、敏捷流程等机制本身不保证好设计；检查它是否真的改善职责、接口和依赖，谨慎对待使层级紧密耦合的实现继承。性能设计先了解昂贵操作，在关键路径上做自然高效的选择；优化前测量定位，优化后复测。只有复杂度换来了可验证且有意义的性能收益，才保留相应复杂度；简单设计往往也更高效。

## 执行检查清单

### 系统设计

- [ ] 主要模块分别封装什么知识/变化？调用者为完成常见任务必须知道的内容是否最少而完整？
- [ ] 是否存在信息泄漏、按执行时序切分导致的重复知识、抽象重复的相邻层或透传接口？
- [ ] 合并/拆分、通用/专用、内部决策/外部配置的取舍，是否按全系统依赖、接口成本和真实使用场景比较过？
- [ ] 是否比较过关键备选方案；增量是否在形成或改善抽象，而不只是增加功能？
- [ ] 错误契约、默认行为和性能目标是否清楚；必要的复杂度是否有证据和明确归属？

### 编写代码

- [ ] 先定义简洁、完整的接口意图与契约，再实现；实现是否隐藏机制而非把复杂度推给调用方？
- [ ] 是否能消除不必要的特例、重复逻辑、无效透传、无谓配置或可避免的错误分支？
- [ ] 名称是否准确、项目风格是否一致；读者能否据此快速形成正确理解？
- [ ] 注释是否记录代码不显然的行为、理由、约束或不变量，而非复述代码；改动后是否同步更新？
- [ ] 新增性能复杂度是否来自测量或明确需求；是否用复测确认收益？

### 代码审查

- [ ] 除了“能工作”，是否评估常见改动的影响面、认知负担及未记录的依赖？
- [ ] 新模块是否足够深；接口是否被特例、实现细节、访问器或过多错误条件污染？
- [ ] 拆分是否真的降低整体复杂度，还是仅增加接口、跳转、编排和重复？合并是否会混淆不同职责？
- [ ] 错误处理是否必要、语义明确且在适当位置；是否存在调用方只能重复捕获/忽略的异常？
- [ ] 命名、注释和实现是否一致、对新读者是否显而易见；注释有没有过期或误导？
- [ ] 是否遵循既有约定；若引入例外，是否有足够理由和覆盖完整的迁移方案？
- [ ] 优化带来的复杂度是否有可复现的性能数据支撑，且收益足以抵偿维护成本？
