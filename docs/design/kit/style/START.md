# 风格拆解流程（给 agent 的操作手册）

**目标**：把一个成熟产品的界面风格**忠实地复刻**成一个**基础风格包**，放进风格库。
**唯一的检验标准**：只凭这个风格包去做**别的**软件（笔记、番茄钟、音乐播放器……），做出来的东西**有没有原版的感觉**，像不像同一个团队做的另一个产品。

这一步**不加任何个人喜好**，不"改进"原版，原版有你不喜欢的地方也照样保留。用户想要的修改，在设计软件时从基础风格开**分支**来做（见 `../design/START.md` 第 1 步和第 6 步）。这样基础风格永远是原版的样子，可以开出很多不同的分支。

**你的角色**：协调者。你负责和用户对话、准备文件、组织对比、整理结果；采集、拆解、复刻、对比、打包这些活交给**子 agent**（新开的干净会话），每次只给它下面写明的文件，不要口头补充。

---

## 总览

| 步 | 做什么 | 谁做 | 产出 |
|---|---|---|---|
| 1 | 定参考产品和采集范围 | 你 + 用户 | `TARGET.md` `NAME.md` |
| 2 | 用浏览器采集原版的真实样式数值 | 能控制浏览器的子 agent + 用户登录 | `capture/` |
| 3 | 拆解，写规范草稿和 token | 子 agent | `analysis.md` `DESIGN-draft.md` `tokens.css` |
| 4 | **延续验证**：只凭规范做 3 个别的小软件 | 3 个子 agent 并行 → 用户看 | `apps/` |
| 5 | 不像就回第 3 步修订，直到有原版的感觉 | 循环 | — |
| 6 | 打包成组件 CSS + 精简规范 + 检查脚本 | 子 agent | 风格包 |
| 7 | 查矛盾 | 子 agent | — |
| 8 | 用打包好的风格包再做一次小软件，确认没丢感觉 | 子 agent → 用户看 | 入库 |

工作目录建议：`<工作区>/style-<名字>/`。每个子 agent 各开一个干净目录，只复制它需要的文件进去。

---

## 第 1 步：准备（你和用户）
1. **参考哪个产品**，看的是它的哪部分（产品界面，不是官网营销页）。一次只拆一个产品
2. **采集范围** → 写 `TARGET.md`：参考产品的网址、要不要登录；这个风格以后**可能**用在哪类软件上（例如"文档 / 知识库类"），据此列出必须覆盖的界面和组件（例如代码块、公式、评论、深色模式、手机端）。这里讲的是**覆盖范围**，不是好恶
3. 名字和类名前缀 → `NAME.md`。基础风格用参考产品命名（例如 `notion` / `nt-`）
4. 准备一个**只有演示内容**的账号或工作区：截图会被保存下来，不要用真实工作区；演示内容要能覆盖第 2 条列出的组件（比如放一个代码块、一个公式）

## 第 2 步：采集（能控制浏览器的子 agent）
**交给**：`prompts/capture.md`（采集说明）+ `tools/extract-styles.js`（注入页面的采集脚本）+ `TARGET.md`
**子 agent 会做**：用 Playwright 之类的工具打开原版（1440×900、浅色），逐个界面截图，并读取：
- 每个元素的**计算样式**统计：颜色、字体组合、间距、圆角、阴影、边框、控件高度、图标尺寸
- **真实的动画参数**：时长、缓动、起止关键帧
- hover 前后的样式差异、焦点样式
- 关键组件的完整盒模型和文字属性

**用户要做**：需要登录的产品，由用户在弹出的浏览器里**手动登录**，子 agent 不碰账号密码
**拿回**：`capture/`（`manifest.md`、`screenshots/`、`extract.json`、`focus.json`、`components.json`、可选的录屏）
**你检查**：`manifest.md` 里的失败项、"有可见动画但未捕获"的项。TARGET 要求覆盖、却没采到的，补采
**没有浏览器自动化时**：让用户按 capture.md 的清单手动截图，在开发者工具里读关键组件的样式。数据会粗一些，在 `DECISIONS.md` 里注明

> Notion 那次：交给 Codex 执行，拿回了 8 个界面、7 组交互动画、hover / focus 数据和 30 多个组件的精确样式，非常详细。采集脚本当时有个 bug（只在 hover 时出现的元素记成空值），已经修好。

## 第 3 步：拆解（子 agent）
**交给**：`prompts/decompose.md` + `capture/` + `TARGET.md`
**子 agent 会做**：按六层（信息架构、视觉层级、视觉系统、交互、动效、细节）逆向还原设计决策，每个数值标 `[测量]` 或 `[估计]`；品牌资产（logo、插画、自有图标集）单独列出，其余视觉特征**全部保留**
**拿回**：`analysis.md`（拆解记录）、`DESIGN-draft.md`（风格规范草稿）、`tokens.css`（全部数值）
**你做**：读 analysis 末尾的「缺口」，和用户确认哪些回第 2 步补采、哪些先估计；建 `DECISIONS.md`（模板 `templates/DECISIONS.style.md`），记下采集日期、浏览器、视口，以及缺口怎么处理

## 第 4 步：延续验证（3 个子 agent 并行 → 用户）
这是整个流程的核心：**只凭规范，能不能把这个风格延续到别的软件上**。
1. 从 `templates/extend-tasks/` 里选 3 个小软件，要覆盖不同类型：
   - 一个和原版同类的（例如原版是 Notion，就选 `notes.md` 简单笔记）
   - 一个简单的工具（`pomodoro.md` 番茄钟）
   - 一个主题差别很大的（`music.md` 音乐播放器）
   - 也可以自己写一个，格式照着模板：几个界面、几个交互，不要求做得很详细
2. 每个小软件派一个子 agent：`prompts/extend.md` + 任务文件（改名为 `TASK.md`）+ `DESIGN-draft.md` 和 `tokens.css`（放进 `style/`）
   - **不给原版截图和 capture**：给了它就会照着截图画，检验不出规范本身的问题
   - 拿回：`app/`、截图、`REPORT.md`（规范里不清楚、只能自己猜的地方）
   - 并行派的时候，在每个 `TASK.md` 末尾写上它专用的端口（例如 5401、5402、5403），不然几个子 agent 会抢同一个端口、甚至看到别人的页面
3. **给用户看**：启动三个软件，给 URL；旁边放两三张原版截图作参照。只问一个问题："**这些像不像原版团队做的另一个产品？哪里不像？**"。不问他喜不喜欢：喜好是设计软件时开分支的事
4. 用户的话原样记进 `reports/FEEDBACK.md`；三个 `REPORT.md` 也放进 `reports/`

## 第 5 步：修订，直到有原版的感觉
- 不像 → 再派一个子 agent 做第 3 步，目录里加上 `reports/`（`decompose.md` 会按修订模式**整份重写**，回到 capture 找原版的真实值），然后重做第 4 步。不要自己去改规范
- **通过的条件**：用户认为三个软件都有原版的感觉；三份 `REPORT.md` 里没有"整块缺失"的大组件
- 一般 1～3 轮。超过 3 轮还不像，多半是采集缺了东西：回第 2 步补采

## 第 6 步：打包（子 agent）
**交给**：`prompts/extract-css.md` + `DECISIONS.md` + `DESIGN-draft.md` + `tokens.css` + `analysis.md` + 通过验证的小软件（放进 `apps/`）+ `NAME.md`（可选：`styles/` 里一个现有风格包作为 `example/`，只参考文件形式）
**子 agent 会做**：从这几个小软件的实际 CSS 里**提取**出组件类（比从文字重新实现准），文字规范精简到只写判断
**拿回**：`tokens.css`、`<名字>.css`（组件类）、`components.html`（样板页）、`DESIGN.md`（≤150 行）、`checks/lint.mjs`、`DECISIONS.md`、`CHANGELOG.md`、`MIGRATION.md`
**为什么要打包**：纯文字规范写到几百行后，执行的人每次都要重新理解再自己实现，矛盾越来越多。外观由 CSS 承载以后，成本降了约四成，风格能稳定复现

## 第 7 步：查矛盾（子 agent）
1. 派一个子 agent：`prompts/check-style.md` + 风格包（放进 `style/`）→ `CONSISTENCY.md`
2. 有"高"级问题：把它放进 `reports/`，派子 agent `prompts/rebuild-style.md` 整份重建（不要自己逐条修补，补丁会制造新矛盾），再查一次
3. **什么时候停**：没有看得见的显示问题、没有引用不存在的东西。不要追求问题数归零

## 第 8 步：复验并入库
1. **再做一次**：子 agent 用**打包好的风格包**（这次会用组件类和 lint）做 `prompts/extend.md`，任务换一个没做过的（例如 `templates/extend-tasks/task-manager.md`）。确认打包没有丢感觉
2. 给用户看，问同一个问题："像不像原版团队做的另一个产品？"
3. **入库**：
   - 风格包放进 `styles/<名字>/`
   - `capture/`、`analysis.md`、几个小软件的截图放进 `styles/<名字>/source/`（以后开分支、或者原版改版后重新对比都用得上）
   - 在 `styles/README.md` 加一行：名字、类型（基础）、一句话特点、适合什么软件、来源、采集日期

## 风格库的结构
```
styles/
├── README.md                  # 索引：每个风格包是基础还是分支、一句话特点、适合什么
├── <基础名>/                   # 基础风格包：忠实复刻原版（本流程的产出）
│   ├── tokens.css  <名字>.css  DESIGN.md  components.html  checks/  DECISIONS.md  CHANGELOG.md
│   ├── source/                # 采集数据和复刻对比（证据）
│   └── branches/
│       └── <分支名>/           # 分支：在基础上按某个用户的喜好修改（设计流程里产生）
│           ├── BRANCH.md      #   基于哪个基础版本、改了什么、为什么
│           └── （完整的风格包文件）
```
基础风格只在**原版改版、或者发现复刻得不准**时才改，改动走第 3～8 步。

## 遇到手册没写到的情况
停下来告诉用户你打算怎么做，得到同意再继续；记一条到 `source/流程问题.md`（发生了什么、手册哪里没写、怎么处理的）。
