# 设计流程（给 agent 的操作手册）

**目标**：从用户一个模糊的想法出发，用一个现成的风格包，和用户一起把软件的界面设计出来，最后得到**产品文档 + 可运行的界面原型**。

**你的角色**：协调者。你和用户对话、整理文档、做校准页；写界面代码、重建文档、查矛盾这些活交给**子 agent**（新开的干净会话），每次只给它下面写明的文件。

**这条路走通过**：在一个个人知识库软件上从采访走到了套好风格的完整原型（第 1～6 步和第 9 步验证过；第 7、8 步还没验证，标了 `[未验证]`）。

---

## 和用户打交道的规矩（全程适用）
用户通常**没有设计背景，说不清想要什么，但看到了能挑**。
1. **给选项，不让他描述**。说不清的地方给 2～4 个具体选项，每个配一句取舍；能渲染出来的就渲染出来给他看
2. **每次最多问 3 个问题**。每一轮开头说清楚：这一轮要定什么、为什么现在定
3. **预选推荐**。每个选择都先标好你推荐哪个、理由一句话。用户回"按推荐"就是同意
4. **不替他编需求**。你觉得应该有的东西标【建议】，由他决定
5. **注意疲劳**。他说"好累""挑花眼了""完全是猜着选"时，立刻减少选择：只留最关键的，其余用推荐
6. **给看的东西要能直接打开**：启动本地服务，给 URL
7. 告诉他：布局和风格的选择**都可以撤回**，原型很便宜

---

## 总览

| 步 | 做什么 | 谁做 | 用户做什么 |
|---|---|---|---|
| 1 | 选风格包 | 你 | 看样板页，选一个 |
| 2 | 采访 → 产品文档草稿 | 你 | 回答 3～4 轮问题，审阅草稿 |
| 3 | 理清概念（对象多时才做） | 你 | 答 2～4 道选择题 |
| 4 | 布局探索（**不给风格包**） | 子 agent | 只看 3～4 个关键区域，挑方案 |
| 5 | 套用风格包 | 子 agent | 裁决冲突清单，看成品 |
| 6 | 校准说不清的视觉问题 | 你做页面 | 排名 |
| 7 | 逐页精修 `[未验证]` | 子 agent | 确认问题清单 |
| 8 | 状态与动效 `[未验证]` | 子 agent | 走流程、选动效 |
| 9 | 随时：改需求、重建文档 | 子 agent | — |

每一步结束：① 用户确认 ② 他拍板的事写进决策记录 ③ git commit（如果项目在 git 里）。

---

## 项目目录和两条铁律
```
<项目>/
├── DECISIONS.md      # 产品决策记录（唯一的事实来源），模板 templates/DECISIONS.product.md
├── PRODUCT.md        # 产品文档，从 DECISIONS 重建
├── CONCEPT-MODEL.md  # 概念模型（第 3 步，可选）
├── style/            # 选用的风格包（整个复制过来）；风格方面的决策写在 style/DECISIONS.md
├── project/          # 只有本产品才有的组件：DESIGN.project.md、project.css、project-tokens.css、components.html
├── app/              # 原型代码
├── calibration/      # 校准页和结果
└── reports/          # 子 agent 的报告；流程问题.md
```
1. **用户拍板的事只追加到决策记录**：产品的写 `DECISIONS.md`（P1、P2…），风格的写 `style/DECISIONS.md`（接着原有编号）。推翻旧决定时新写一条，注明推翻了哪条
2. **文档只重建，不打补丁**：PRODUCT.md 或风格包要更新时，派子 agent 按决策记录**整份重写**，再派另一个子 agent 查矛盾（第 9 步）。不要自己逐节改旧文档：前文会残留被推翻的说法，越改越乱

---

## 第 1 步：选风格（你）
风格库 `styles/` 里有两种风格包（见 `styles/README.md`）：
- **基础风格**：忠实复刻某个成熟产品，例如 `styles/notion/`
- **分支**：某个基础风格按某位用户的喜好改过的版本，例如 `styles/notion/branches/quietpaper/`。每个分支的 `BRANCH.md` 写了它和基础的差别

1. 用本地服务打开候选的 `components.html` 给用户看，各配一句话（适合什么软件；分支还要说它改了基础的什么）
2. 用户选一个：
   - 选了现成的分支 → 直接用，以后的修改接着在这个分支上做（项目结束时可以存成新分支，见「完成」）
   - 选了基础风格 → 原样用；后面一旦校准出个人偏好，就形成本项目的分支
   - 都不喜欢 → 问他喜欢哪个现成软件的样子，先走「风格拆解流程」（`../style/START.md`）拆出基础风格；或者先选最接近的继续，以后整包替换（布局不受影响）
3. 把选中的风格包整个复制到 `<项目>/style/`；建 `DECISIONS.md`，第一条写"使用风格包 X vY"

## 第 2 步：采访 → 产品文档草稿（你）
1. **最多 3～4 轮**，只问决定全局的问题：
   - 这是什么、给谁用、最重要的 3～5 件事
   - 平台：桌面 / 手机 / 平板，各在什么场景用
   - 有哪些主要视图，每个视图的**形态**：用选项问，例如"代码视图更像 A. 文档里的代码块，还是 B. VS Code 那样的编辑器？"
   - **第一期做到哪**：把以后的功能明确划出去，否则布局会被未来功能撑爆
2. 然后**一次性写出完整的 `PRODUCT.md` 草稿**（模板 `templates/PRODUCT.template.md`）。没问到的部分按合理默认值写，标【建议】。必填：
   - 每个视图的形态
   - **能力 × 视图矩阵**：评论、搜索、AI、分享……在每个视图里各怎么做。逐格填，空着的格子就是以后会漏掉的功能
   - 第一期范围
3. 请用户审阅：逐条打勾、划掉、改写。只对有争议的地方追问
4. 审阅结果写进 `DECISIONS.md`

> 知识库项目那次：逐节采访问了 20 轮，用户明显疲劳（"已经问了我整整 9 轮了还在问"）。改成"少问几轮 + 出草稿让他审"后好得多：审阅比回答容易。

## 第 3 步：理清概念（你；产品对象多时才做）
产品里有多种互相关联的对象（例如"项目、会话、执行环境、沙箱"），而且用户自己可能都没想清楚它们的关系时才做。只有一两种对象的软件（记账、番茄钟）跳过。
1. 写 `CONCEPT-MODEL.md`（模板 `templates/CONCEPT-MODEL.template.md`）：
   - 对象表（是什么、生命周期）
   - 关系图
   - **这个产品由哪几种成熟产品叠加而成**（例如"Notion + IDE + 多 agent 编排"），每块对应哪些对象、第一期优先级
2. 附 2～4 道选择题，每题带推荐。答案写进 `DECISIONS.md`
3. **还没想清楚的对象，对应的界面区域不进入第 4 步**，先用最简单的方案占位，标"暂定"

> 知识库项目那次：没做这一步，结果用户到看成品时才发现"审批按风险分组根本没法判断"，根源是执行环境、会话、项目的关系没理清，返工了一轮。

## 第 4 步：布局探索（子 agent；不给风格包）
**为什么不给风格包**：风格包是从某个参考产品拆出来的，同时给的话，子 agent 会照搬参考产品的布局（比如把代码视图做成 Notion 页面里的一个代码块），而不是按你的产品该有的样子做。
1. 你先写 `SLICE.md`：这一轮做哪些视图；哪些**区域**要出多个方案（区域 = 侧边栏顶部、文件树、正文、评论栏、代码视图……）；每个区域你推荐的方向
2. **交给**子 agent：`prompts/layout.md` + `PRODUCT.md` + `SLICE.md` + `CONCEPT-MODEL.md`（如有）
3. **拿回**：`app/`（带方案切换器的可运行原型）、各方案截图、`REPORT.md`（每个方案的取舍、谁在用这种做法、实现难度；PRODUCT 里不清楚的地方）
4. 启动服务给用户看。**只请他看影响最大的 3～4 个区域**，其余直接用推荐。按区域选，不按整套方案选：用户常常想要"A 方案的侧边栏 + C 方案的代码视图"
5. 选择结果写进 `DECISIONS.md`；他对功能本身的意见（"这里缺 X""这个不要"）也写进去
6. REPORT 里 PRODUCT 不清楚的地方：能自己判断的写成【建议】，需要用户定的整理成选择题问他

**检查点**：遮住文字只看色块，能不能分出主次？3 秒内能不能说出每一页是干什么的？

## 第 5 步：套用风格包（子 agent）
1. **交给**子 agent：`prompts/apply-style.md` + `app/` + `style/` + `project/`（第一次可以没有）+ `PRODUCT.md`
2. **拿回**：套好风格的 `app/`、截图、`REPORT.md`，里面有：
   - **冲突清单**：风格包里标 `[模式]` 的默认布局习惯和原型冲突的地方（原型优先）。逐条给用户看，附你的推荐；他的裁决写进决策记录
   - **风格包里不清楚、只能自己猜的地方**，分三类：① 规则自相矛盾 ② 缺组件 ③ 缺数值。这些是风格包自己的问题，存进 `reports/`，攒着给第 9 步重建风格包用
   - **新建的组件类**：确认它们写进了 `project/project.css` 和 `project/DESIGN.project.md`
3. 启动服务给用户看成品。他的意见按下面的「意见怎么分流」处理

**检查点**：`node style/checks/lint.mjs app` 结果为 0；用户看过所有主要视图。

## 第 6 步：校准（你做页面，用户排名）
用户看了成品说"这里颜色不对""这个图标丑""太花了 / 太单调"，但说不出要什么时做。
1. 用 `templates/calibration.html` 做一页，每题 4～6 个方案：
   - **用当前的风格包渲染**，放在真实的界面片段里，只改要比较的那一处
   - 第一个方案放现状作对照；方案覆盖两端（最克制 ↔ 最醒目）
   - 每个方案标一个**设计概念**（"颜色只做锚点""靠明度不靠颜色""最克制"），让用户积累词汇
2. 用户标前三名和最不喜欢的一个，写一句感受
3. 结果写进 `style/DECISIONS.md`，编号用 B1、B2……（表示**本项目在基础风格上的分支**），注明改的是基础的哪一条；感受里的通用规律另写一条（例如"阅读区不加装饰色"），以后没问到的地方按它推。第一次写 B 条目时，在 `style/` 里建 `BRANCH.md`（模板 `templates/BRANCH.md`）
4. 攒几条后，第 9 步重建风格包，再派子 agent 改应用（`prompts/change.md`）

## 第 7 步：逐页精修（子 agent）`[未验证]`
一次一页：
1. **交给**子 agent：`prompts/polish.md` + `app/` + `style/` + `project/` + `PRODUCT.md` + `TASK.md`（写哪一页）
2. 子 agent 只截图自查、列问题清单，不改代码。你把清单给用户确认（他可以删、可以补）
3. 再派一个子 agent，`TASK.md` 里附上确认过的清单，让它改
4. 记下"AI 自查发现几条 / 用户额外发现几条"，写进 `reports/流程问题.md`

## 第 8 步：状态与动效（子 agent）`[未验证]`
- **状态**：按 PRODUCT 的核心流程逐个派子 agent：加载中、空、出错、禁用、长文本和空值、键盘操作（Tab、Enter、Esc）。先列问题，用户确认后再改
- **动效**：用户描述想要的感觉（"侧边栏展开更顺滑"）→ 你写成动效规格（触发 / 起止状态 / 属性 / 时长 / 缓动 / 中断 / 减少动态效果时）→ 做一个对比页，3 个方案（克制 / 自然 / 有表现力）可以反复点 → 用户选 → 写进 `style/DECISIONS.md` 或 `project/DESIGN.project.md`

## 第 9 步（随时）：改需求、重建文档
- **改需求，布局形态不变**（例如"审批改成按项目分组"）：写进 `DECISIONS.md`，写一份 `CHANGE.md`（改什么、影响哪些视图），派子 agent：`prompts/change.md` + `app/` + `style/` + `project/` + `PRODUCT.md` + `CHANGE.md`。比重走第 4、5 步便宜得多
- **重建 PRODUCT**（决策攒了几条、进入下一步之前、或子 agent 报告说 PRODUCT 前后矛盾）：
  1. 子 agent：`prompts/rebuild-product.md` + `PRODUCT.md` + `DECISIONS.md` + `CONCEPT-MODEL.md` + `templates/PRODUCT.template.md`
  2. 另一个子 agent：`prompts/check-product.md` + 新 `PRODUCT.md` + `CONCEPT-MODEL.md`
- **重建风格包**（校准出了新决策，或报告里攒了一批 ① ② ③）：
  1. 子 agent：`prompts/rebuild-style.md`，目录里放 `DECISIONS.md`（风格的）、`style/`、`project/`（含 PRODUCT.md）、`reports/`（报告和上次的矛盾检查）、`apps/`（当前的 app，用来确认没改坏）
  2. 另一个子 agent：`prompts/check-style.md` + 新的 `style/` + `project/`
  3. 新版本复制回 `<项目>/style/` 和 `<项目>/project/`
- **什么时候停**：查矛盾永远能找到新问题，不要追求归零。没有看得见的显示问题、剩下的高级问题都是需要用户拍板的事，就停；把这些事整理成选择题，下次一起问他

## 完成
第一期范围里的每个视图都做了、lint 为 0、用户逐个看过并认可。然后：
1. **保存风格分支**：如果 `style/` 里有 B 条目（本项目改过风格），问用户要不要存进风格库，以后做别的软件也能选。要的话：
   - 补全 `style/BRANCH.md`：一句话特点、适合什么软件、和基础的差异表、用户的通用偏好
   - 把 `style/` 复制到 `styles/<基础名>/branches/<分支名>/`，在 `styles/README.md` 加一行
   - 只放通用的风格；本产品专属的组件（`project/`）不放进去
2. 把 `reports/流程问题.md` 交给用户

## 意见怎么分流
用户的每一条意见、子 agent 报告里的每一条问题，都先问：**写到哪里，下次就不用再说？**

| 意见 / 问题 | 例子 | 写到 |
|---|---|---|
| 功能、视图形态、页面组成 | "代码也要能评论""审批不要按风险分组" | `DECISIONS.md` → 改需求（第 9 步） |
| 用户明确拍板的审美 | "AI 头像用灰色" | `style/DECISIONS.md` → 重建风格包（第 9 步） |
| 说不清的审美 | "看着不舒服" | 先校准（第 6 步） |
| 组件 CSS 的 bug（报告 ①） | "当前项比 hover 还浅" | 直接改那个 CSS 类（单个类的 bug 不用整体重建） |
| 缺组件（报告 ②） | "没有工作区切换器" | 通用的 → 风格包补类；只有本产品有的 → `project/project.css` 补类；都在样板页加示例 |
| 缺数值（报告 ③） | "弹窗宽度没给" | 值得复用的补 token；其余写成规则或先不定 |
| 流程本身的问题 | "早该先问清楚这个" | `reports/流程问题.md` |

**不要直接手改界面代码去迁就一条意见**：代码改了、文档没改，下次重新生成时问题又回来了。

## 子 agent 怎么派
- 每次开一个**新的干净会话**，目录里只放上面写明的文件；不要口头补充。如果你觉得必须补充，说明文档有缺口：先补文档，再派
- 理由：你和用户聊了很多，脑子里有大量没写进文档的意图。干净的子 agent 会把文档的缺口暴露出来，你自己做就发现不了
- 子 agent 的报告放进 `reports/`；它启动的本地服务做完要关掉；同时派几个子 agent 时，给每个指定不同的端口
- 你的环境不能开子 agent 时：自己做，但先把对话里的意图全部写进文档，做的时候只看列出的文件

## 遇到手册没写到的情况
停下来告诉用户你打算怎么做，得到同意再继续；记一条到 `reports/流程问题.md`（发生了什么、手册哪里没写、怎么处理的）。
